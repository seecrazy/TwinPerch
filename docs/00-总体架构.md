# 双栖（TwinPerch）总体架构 v2

> 状态：设计草案 v2 · 2026-11-08
> 基于 v1 方案（Cloudflare-only）的评审修订。

## 1. 本版相对原方案的变化

| # | 变化 | 动因 |
|---|------|------|
| 1 | 传输层与协议解耦：定义统一的传输抽象（`RelayTransport`），传输实现可插拔 | 原方案把"中转方式"焊死在 Cloudflare 上，大陆可达性问题是单点故障 |
| 2 | 邮箱中转从"第三阶段兜底"升级为主干传输；Cloudflare Worker 降为海外/进阶选项 | workers.dev 在大陆被 DNS 污染（含付费账户）；邮箱是唯一零注册门槛且大陆可达的通道 |
| 3 | 推送代理单独立项：opt-in、内容零知识 | iOS 推送必须用开发者的 APNs 凭证（平台约束，任何传输方案绕不开）；原方案"初期不做推送"保留为默认态 |
| 4 | 补齐加密协议规范：前向保密（链棘轮 + 周期 DH 重键）、消息封装、房间鉴权、重配对 | 原方案静态 X25519 共享密钥无前向保密、nonce 管理未定义、房间接入鉴权缺失 |

**不变的核心理念**：密钥只在双方设备上、开发者不运营消息通道、聊天记录只存本地。开发者运营的组件只剩一个 opt-in 的推送代理（且内容零知识）。

一句话：**两个人各自独立，共享一片只有彼此能进的领地；进领地的路有多条，锁和钥匙始终只在两人手里。**

## 2. 分层架构

```
┌───────────────────────────── iOS App ──────────────────────────────┐
│  UI（SwiftUI）：配对 / 会话 / 设置 / 门禁                              │
│  App 门禁：LocalAuthentication（冷启动 + 后台超 5 分钟）               │
│ ┌──────────────────── TwinPerchKit（无 UI 依赖）───────────────────┐ │
│ │  CryptoCore  配对握手 / 链棘轮 / 加解密 / 安全码   ← 加密协议规范   │ │
│ │  Session     会话状态机（链状态、跳过密钥、去重、ACK）               │ │
│ │  Vault       加密本地库（GRDB + 列级 AES-GCM，excludedFromBackup） │ │
│ │  Transport   ── 传输抽象接口 ──                                   │ │
│ │     ├─ EmailTransport        IMAP/SMTP        （主干）             │ │
│ │     ├─ CloudflareTransport   WSS + Durable Object（海外/进阶）     │ │
│ │     └─ PortableRelayTransport 自托管二进制      （第三阶段）        │ │
│ │  PushClient  推送代理客户端（opt-in，默认关）                       │ │
│ └──────────────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────────────┘
        │                                        │
   邮箱（IMAP/SMTP）或 WSS                    APNs 通知（固定文案）
        │                                        │
   第三方基础设施：                          推送代理（开发者运营，
   邮件服务商 / Cloudflare / 自托管 VPS      只见 device_id + 计数）
   —— 只接触密文与路由元数据，不接触任何密钥 ————
```

## 3. 市场 → 主干传输决策

| 目标市场 | 主干传输 | 备选 | 理由 |
|---|---|---|---|
| 中国大陆 | 邮箱（QQ/163/126） | 无（workers.dev 被墙，CF 不可用） | 唯一零部署且可达的通道 |
| 海外（含华人） | 邮箱或 Cloudflare 双选 | 自托管 relay | CF 体验最好（WSS 实时）；邮箱门槛最低 |

该决策不阻塞开发：传输抽象保证两条实现共享同一套加密与会话代码；App 内"连接方式"作为设置项。Phase 0 结束前需定稿（见客户端文档的开放决策表）。

## 5. 设计原则

1. **密码学最小化**：只用 CryptoKit 原语（X25519 / HKDF / HMAC-SHA256 / ChaCha20-Poly1305 / SHA-256），零第三方加密依赖，全部代码可审计。
2. **传输不可信**：任何传输实现只承诺"尽力而为的字节投递 + 乱序容忍"，安全性全部来自密码层。换传输 ≠ 改安全模型。
3. **元数据诚实**：每条传输暴露什么元数据、给谁，写成披露矩阵（传输抽象 §5）并放进产品页，不做无法兑现的隐私宣称。
4. **可审计**：加密协议写成正式规范 + 测试向量，Phase 0 做交叉验证与外部审查，之后才冻结 v1。
