# 推送代理（PushProxy）—— 开发者运营的唯一组件，opt-in

> 为什么必须有：iOS 原生推送只有 APNs，凭证只能来自开发者的 Apple 开发者账号——平台约束，任何传输方案都绕不开。
> 默认态：**关闭**（与 v1 方案"初期不做推送"一致）；用户在设置里 opt-in。

## 1. 架构（Delta Chat 同款模式）

```
relay（邮箱轮询/CF Worker/自托管）                PushProxy（开发者账户上的一个 Worker）
        │  "device_id 有 N 条新消息" ──────────────▶  │
        │                                            │ APNs（固定文案，无内容）
        ▼                                            ▼
   对方离线投递时触发                          iPhone 振铃 → App 醒来 → 从原传输通道拉取密文
```

**代理只知道**：device_id（128-bit 随机数）→ APNs token 的映射 + 消息计数。
**代理不知道**：消息内容、发送方身份、房间、IP。

## 2. API

```
POST /register    {device_id, apns_token, kind}   // App 注册/更新 token
POST /unregister  {device_id}
POST /notify      {device_id, count}              // 仅 relay 持 PUSH_PROXY_KEY 可调（防滥用）
```

APNs payload：`{"aps":{"alert":{"title":"双栖","body":"收到新消息"},"sound":"default"},"n":<count>}`

固定文案，不泄露任何内容与数量关系。v1 **不做** mutable-content 富预览——NSE 解密与生物门禁冲突，二期再评估。

## 3. App 内流程

设置 → 通知 → 开启"即时提醒"：
1. 生成 device_id，`/register`
2. 通知 relay 侧开启 notify（邮箱传输：App 自己发 notify；CF 传输：部署时已注入开关变量）

关闭时 `/unregister` + relay 侧停止。

## 4. 成本与自托管

- 开发者侧：一个 CF Worker + APNs token，情侣量级在免费额度内；规模化也 < $5/月。这是全方案中开发者唯一的运营组件。
- 代理代码开源；但 APNs token 与 App bundle id 绑定，自托管代理仍需开发者签发的 token——诚实写进文档。

## 5. 隐私宣称边界

产品页措辞：**"开启即时提醒后，开发者运营的通知服务会收到一个随机设备编号和新消息条数；消息内容与你们的身份仍然只有你们可见。"**
