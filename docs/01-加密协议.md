# 加密协议规范（TP-Crypt v1 草案）

> 状态：草案。Phase 0 完成交叉验证与外部审查后冻结。
> 实现约束：仅用 CryptoKit（X25519 / HKDF-SHA256 / HMAC-SHA256 / ChaCha20-Poly1305 / SHA-256），零第三方加密库。

## 1. 威胁模型

**保护目标**：消息与附件内容、本地聊天库。

**明确不保护**（写进产品页的诚实清单）：
- 元数据：时间、双方邮箱地址/IP、消息频率与大小——对传输方与网络可见
- 传输方主动丢弃或延迟消息——**可检测**（链序号空洞 + ACK 超时触发"连接不稳定"提示），不可阻止
- 已解锁且通过生物验证的设备上的内容——门禁防他人，不防机主
- 双方设备同时被攻破

**信任假设**：
- 面对面扫码通道可信（无中间人）
- iOS Keychain 硬件保护成立
- 传输方（邮件服务商 / Cloudflare / VPS 主机商）是"诚实但好奇"，且可能被胁迫——因此**传输方持有的任何秘密都不允许具备解密能力**（房间鉴权密钥的残留风险见 §8，已明确接受）

## 2. 密钥体系

每台设备持有：

| 密钥 | 用途 | 存放 |
|---|---|---|
| IK（身份密钥） | X25519，首次启动生成，构成安全码与 DH 输入 | Keychain `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` |
| vault_key | 256-bit，本地库列级加密 | Keychain 同上 |
| 会话状态（链密钥、跳过密钥表） | 棘轮运行态 | 本地库内列级加密（vault_key 保护） |

注意事项：
- **X25519 私钥无法放入 Secure Enclave**（SE 仅支持 P-256）。宣传文案不得声称"密钥在 Secure Enclave"；生物识别只用于 App 门禁（LA 框架）。
- Keychain 不绑生物识别 ACL（`kSecAccessControlBiometryCurrentSet`），保证推送唤醒的后台收发不被弹窗阻塞；门禁在 UI 层完成。

## 3. 配对与握手（X3DH 简化版，面对面）

前提：A、B 各自首次启动已生成 IK。

1. A 展示 **QR_A**：`{v, ik_a_pub, ek_a_pub, sid, nonce_a}` —— sid = 16 字节随机 session_id；EK_A 为新鲜临时密钥
2. B 扫描后本地生成 EK_B，展示 **QR_B**：`{v, ik_b_pub, ek_b_pub, sid, nonce_b}`
3. A 扫描 QR_B。双方各自计算：

```
DH1 = X25519(IK_self_priv,  IK_peer_pub)
DH2 = X25519(IK_self_priv,  EK_peer_pub)
DH3 = X25519(EK_self_priv,  IK_peer_pub)
DH4 = X25519(EK_self_priv,  EK_peer_pub)

master = HKDF(DH1 ‖ DH2 ‖ DH3 ‖ DH4,
              salt = nonce_a ‖ nonce_b,
              info = "TP-crypt-v1")
```

DH4 的临时密钥提供握手前向保密：事后 IK 泄露也无法解密历史（前提：EK 私钥握手后立即销毁）。

4. 双方从 master 派生：

| 派生项 | info | 用途 |
|---|---|---|
| root_key | `"root"` | 棘轮根密钥 |
| chain_A→B | `"chain-a"` | A 的发送链（B 的接收链） |
| chain_B→A | `"chain-b"` | B 的发送链（A 的接收链） |
| k_room | `"room-auth"` | 房间鉴权密钥（仅推送型传输使用，见 §8） |
| room_id | `"room-id"`[0..<16] | 房间标识（推送型传输） |
| safety_code | — | 见 §7 |

5. 双方屏幕并排显示**安全码**，人工比对一致后配对完成。

## 4. 链棘轮：对称哈希链 + 周期性 DH 重键

原方案的问题：静态 X25519 协商出单一共享密钥用到底——无前向保密，nonce 管理无定义。本节替换之。

### 4.1 发送（每条消息）

发送方维护 `chain_key`（32 字节）与 `index`（从 0 递增）：

```
chain_key_n+1 = HMAC-SHA256(chain_key_n, 0x01)
message_key   = HMAC-SHA256(chain_key_n+1, 0x02 ‖ LE64(index))
enc_key       = HMAC-SHA256(message_key, "enc")[0..<32]
nonce         = HMAC-SHA256(message_key, "nonce")[0..<12]
```

发送后旧 chain_key 与 message_key 即覆盖销毁。message_key 每条消息唯一，nonce 由其派生——**随机碰撞问题从结构上消除**。

### 4.2 接收

按 `(session_id, 发送方, chain_index)` 匹配链。**乱序处理**：收到 `index = n+k` 而 `n` 未到时，先派生并暂存 k 个跳过密钥（skipped store，上限 4096 条）。上限耗尽触发重同步（§4.4）。

### 4.3 DH 重键（ratchet step）

触发条件（任一）：
- 单链每 500 条消息，或距上次重键超过 7 天
- 收到 SYNC_REQUEST

**v1 步进规则（实现精化）**：只有会话发起方（A）可自发 step；响应方（B）仅在收到
SYNC_REQUEST 后 step。已发出 syncRequest 但未收到对方 step-carrier 期间，双方都推迟
新的 step，避免 root 分叉（step-carrier 携带 root 指纹，任何不一致按不可恢复分歧处理，
fail-safe 要求重新配对）。

step 方生成新临时密钥 EK_new，其公钥随**本 dh_step 的每条消息头**携带（容忍 carrier
丢失；step 0 期间不携带）。对方收到 dh_step 增量 + ek_pub 后计算：

```
dh_out    = X25519(EK_new_priv, IK_peer_priv 所对应的公钥)   // 双方可算同一值
root_key' = HKDF(root_key, ikm = dh_out, info = "root-step")
新发送链   = HKDF(root_key', info = "chain-a" | "chain-b")   // 按角色取
dh_step  += 1
```

### 4.4 重同步

链空洞超过上限（长时间离线、丢消息）时，接收方发 `SYNC_REQUEST` 控制帧；对方执行一次 DH 重键，整链重置，跳过密钥作废。

## 5. 消息封装（Envelope，传输无关的二进制）

外层再按传输封装（邮箱 MIME 附件 / WS base64），本层只有一种格式：

```
偏移  字段          说明
0     version     u8  = 1
1     type        u8  0=文本 1=附件清单 3=ACK 4=已读 5=SYNC_REQUEST 6=KEY_NOTICE
2     dh_step     u16 LE
4     chain_index u64 LE
12    session_id  16 字节
28    ek_pub      32 字节（当前 dh_step 的临时公钥；step 0 或本步无重键时全 0。
                   整个 dh_step 期间每条消息都携带，容忍 carrier 丢失）
60    root_fp     4 字节（HMAC(k_confirm, root)[0..<4]，链连续性校验）
64    nonce       12 字节（= HMAC(message_key, "nonce")[0..<12]，确定性派生）
76    ct_len      u32 LE
80    ciphertext  ct_len 字节 = ct ‖ tag(16)（ChaCha20-Poly1305，不含 nonce）
```

**AAD = version ‖ type ‖ dh_step ‖ chain_index ‖ session_id ‖ ek_pub ‖ root_fp ‖ nonce**
（ek_pub、root_fp 必须入 AAD，防止头篡改导致密钥分歧）。

密文内层（明文载荷，CBOR）：

```
{ "t": 内容类型, "body": "...", "mid": "uuid",
  "ts": 发送方时间戳,
  "ack": <已收到的最大 index>,       // 捎带回执
  "read": <已读到的最大 index> }     // 捎带已读
```

ACK / 已读优先捎带在普通消息里；无消息可发时用 type=3/4 控制帧单独发。**控制帧同样加密**——传输方连"这条是回执还是聊天"都看不到。

## 6. 防重放与去重

- 传输层 at-least-once → 接收方以 `(session_id, sender, chain_index)` 去重
- 已消费的 index 直接静默补发 ACK
- 重放旧密文：对应 message_key 已销毁，Poly1305 校验必然失败

## 7. 安全码与重配对

- 安全码 = SHA-256(initiator_pub ‖ responder_pub) 前 8 字节，以 **16 个 hex 字符、4 组×4** 展示，配对时与每次进入设置页时人工比对。（v1 采用 hex 而非 emoji 表：零维护成本且两实现逐字节一致。）
- **重配对**（丢机/换机）：新配对产生新 session_id，会话时间线上以"安全码已变更"分隔条明示；旧 session 消息保留只读。KEY_NOTICE 控制帧用于旧设备主动通知（设备未丢、主动换机时）。

## 8. 房间鉴权（仅推送型传输：CF / 自托管 relay）

```
C→S  {t:"hello",    room: room_id_hex}
S→C  {t:"challenge", n: base64(32B 随机)}
C→S  {t:"auth",     mac: base64(HMAC-SHA256(k_room, n))}
S→C  {t:"ok", backlog: N}
```

服务端持有 k_room 用于校验。**接受风险（须写入产品文档）**：被胁迫的传输方可借 k_room 伪装连接、观测元数据、丢弃消息；但无法伪造能通过对方 Poly1305 校验的消息、无法读取任何内容。丢弃行为由链序号空洞 + ACK 超时暴露。

## 9. 安全属性表

| 属性 | 结论 | 机制 |
|---|---|---|
| 内容机密性 | ✓ | ChaCha20-Poly1305，per-message key |
| 历史前向保密（设备密钥当前泄露，历史已发消息） | ✓ | 链式 HMAC 单向派生，密钥即用即毁 |
| 握手前向保密（事后 IK 泄露，历史） | ✓ | DH4 临时密钥，EK 即毁 |
| 未来保密 / 自愈（PCS） | 部分 ✓ | 周期 DH 重键：攻破链密钥但未攻破 IK 者在下一次重键后失联 |
| 身份伪造 / MITM | ✗ | 面对面 QR 交换 + 安全码人工比对 |
| 重放 / 篡改 | ✗ | index 去重 + AAD |
| 完整 IK 泄露 | 需重配对 | 新 session_id + 安全码变更明示 |
